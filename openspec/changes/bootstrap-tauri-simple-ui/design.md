## Context

OpenSerial 当前处于规划阶段，仓库内已有产品、架构和视觉设计文档，但没有可运行的应用代码。现阶段最需要的是一个可启动、可迭代的 Tauri 工作台壳层，用来验证文档中定义的三栏布局、视觉克制原则，以及前端 UI 与 Rust 宿主层的协作边界。

这个 change 的直接使用者是后续继续实现串口、日志和过滤能力的开发者。约束来自两处：

- `docs/design.md` 要求日志区保持主视觉中心，界面低饱和、低装饰、长时间可读。
- `docs/architecture.md` 要求应用分成 Tauri 宿主层、核心层、状态层和 UI 层，并为未来的串口命令与事件推送预留边界。

## Goals / Non-Goals

**Goals:**
- 建立一个基于 Tauri + Rust + React + TypeScript 的可运行桌面应用骨架。
- 实现主工作台的首版布局：顶部工具栏、左侧连接区、中间日志区、右侧分析区、底部发送区。
- 使用占位数据和可点击控件模拟主要交互，验证信息架构和视觉层级。
- 为后续真实串口命令、事件订阅和状态管理留下明确的模块与接口位置。

**Non-Goals:**
- 不实现真实串口枚举、打开、关闭、读写。
- 不实现完整的过滤引擎、搜索引擎、日志虚拟列表或解析管线。
- 不引入复杂状态库、插件系统或持久化层。
- 不在本 change 中承诺完整工业级响应式设计，只覆盖桌面窗口下的合理压缩与折叠。

## Decisions

### 1. 使用 Tauri + React + TypeScript 的最小骨架，而不是先做纯前端原型

直接从 Tauri 脚手架起步，可以尽早把 UI 代码放进未来真实运行环境，避免先做一套纯浏览器原型，后续再重新适配桌面宿主边界。Rust 宿主层即使暂时只暴露占位命令，也能固定目录、命名和调用方式。

备选方案：
- 先用纯 Vite/React 原型验证 UI：启动更快，但后续仍要补 Tauri 层，容易形成第二套入口。
- 先只写 Rust 宿主空壳：无法验证最关键的工作台布局，价值较低。

### 2. 首版采用静态工作台模块划分，优先保证主日志区稳定

前端按 `app/`、`components/`、`modules/`、`styles/`、`types/` 组织，并让工作台页面直接组合连接区、日志区、分析区和发送区。这样符合架构文档，也便于后续把每个区域独立增强。

备选方案：
- 一开始就做深层路由和多页面结构：当前没有必要，且会分散注意力。
- 把所有 UI 写进单文件：初期速度快，但会破坏后续模块扩展。

### 3. Rust 宿主层只提供最小 command/event 占位接口

Rust 侧先建立 `commands/`、`state/`、`app/` 基础目录，并提供例如 `list_ports` 的 mock 返回值或空实现占位，让前端调用链、类型和错误展示路径先稳定下来。高频日志流先在前端本地 mock，不在这个阶段引入真实事件通道压力。

备选方案：
- 完全不写 Rust command，只做静态 UI：后续再补边界时容易改动入口结构。
- 直接连真实串口：超出当前 change 目标，也会把 UI 验证和底层调试混在一起。

### 4. 视觉实现遵循低饱和桌面工具风格，不引入重卡片和强动效

样式层采用 CSS 变量定义中性色、雾蓝强调色、状态色和密度值。布局通过细边框、轻背景差和等宽日志字体建立层级，不使用重阴影、霓虹色或营销式动效。界面压缩时优先折叠右侧分析区，再压缩左侧连接区。

备选方案：
- 使用现成重型组件库快速拼装：能提升初速，但视觉容易偏离文档基线。
- 过早自建复杂 design system：当前范围过大。

## Risks / Trade-offs

- [风险] 首版使用 mock 数据，容易让人误以为串口链路已具备 → 缓解：在设计和任务中明确 mock 边界，命令命名和模块位置为真实实现预留但不伪装完成。
- [风险] 过度设计目录与模块，导致初始化成本偏高 → 缓解：只建立文档中已经稳定的主目录，不提前细分未使用子模块。
- [风险] 没有真实日志流时，日志区的密度和滚动体验验证不充分 → 缓解：准备覆盖收发、错误、搜索高亮等典型状态的占位日志样本。
- [风险] 不引入状态库可能在后续扩展时重构 → 缓解：当前先把状态集中在工作台级别，等串口事件和过滤逻辑成型后再决定是否升级到专门状态库。
